# ボートレース予想アプリ 設計書

最終更新: 2026-11-12

## 目的と前提

各艇の勝つ確率を出し、期待値が高い買い目だけを推奨し、結果を自動で答え合わせするアプリを作る。

- **ゴール**：的中率より「確率の正確さ」と「回収率」を上げる。払戻率は約75%なので、確率が正確でなければ長期では負ける。
- **対象**：最初から全国24場。場の違いは、場ごとのコース傾向や水面の種類などの特徴量で表す。
- **実行環境**：GitHub Actions（定時実行）。ジョブは自宅PC（セルフホストランナー）で動かす。言語はPython。
- **購入**：手動。アプリは推奨買い目と、実際に買った記録の両方を持つ。
- **通知**：推奨買い目が出たときだけ、DiscordのWebhookで即時通知する。通知には場名・レース番号・締切時刻・買い目・期待値・推奨金額を載せる。WebhookのURLはGitHub Secrets（DISCORD_WEBHOOK_URL）に保存する。その他は記録表とダッシュボードで見る。
- **実装**：この設計書をもとにGeminiに段階ごとに実装を依頼する。

## 全体の流れ

| 時刻 | 処理 |
| --- | --- |
| 朝 8:00 | 番組表を取得 → 直前情報なしで予想 → 1着確率を記録 |
| 締切15分前 | 直前情報・3連単オッズを取得 → 確率を更新 → 期待値1.15以上の目を推奨しDiscord通知（なければ見送り） |
| 夜 22:00 | 成績を取得 → 自動で答え合わせ → 集計・ダッシュボード更新 |
| 毎週月曜 3:00 | 4モデルを再学習 |

買うかどうかを決めるのは締切前の処理で、朝と夜はその準備と検証にあたる。

## データ取得

公式サイトのデータを集める。アクセスは数秒以上の間隔をあけ、必要な分だけ取る。取得済みのデータは再取得しない。

| データ | 中身 | 取得タイミング | 主な用途 |
| --- | --- | --- | --- |
| 番組表 | 出走選手、枠、級別、勝率、モーター・ボート番号と2連率 | 前日夜〜当日朝 | 予想の入力 |
| 競走成績 | 着順、進入コース、スタートタイミング、決まり手、払戻、返還艇 | レース後（日別ファイル） | 学習データ、答え合わせ |
| 直前情報 | 展示タイム、進入、チルト、部品交換、風向・風速、波高、欠場 | 締切の約15分前 | 確率の更新 |
| オッズ | 3連単（締切15分前と確定） | 締切前・レース後 | 期待値の計算 |

### 期間の使い分け

| 用途 | 期間 | 理由 |
| --- | --- | --- |
| メインの予想モデル | 2012年以降（直近ほど重く） | 2012年のプロペラ制度変更で、モーターの影響の出方が変わったため |
| 選手の年齢カーブ・経歴の特徴 | 取れる限り全期間 | 年齢による衰えはキャリア全体でしか見えないため |
| 場ごとのコース傾向 | 直近3〜5年 | 水面改修やルール変更で傾向が変わるため |

- 公式サイトで一括取得できる最も古い年を、最初に確認する。それより前は無理に集めない。
- 過去データは年・月別のParquetファイルに分け、Googleドライブの専用フォルダに置く。GitHub Actionsからは、本人のGoogleアカウントで発行したOAuthのリフレッシュトークン（GitHub Secretsに保存）でアクセスする。個人のGmailアカウントではサービスアカウントは容量を持てず書き込めないため使わない。毎回全部は落とさず、必要な年・月のファイルだけ取得する。リポジトリ内のSQLiteは直近分と記録だけにする。

### 取得の注意点

- **過去の直前オッズは存在しない**：公式の過去データは確定オッズだけ。第1段階から「締切15分前オッズ」と「確定オッズ」を毎日両方保存し、締切までのオッズの動き方を記録する。
- **過去の直前情報**：日別の成績ファイルに含まれる項目（展示タイム、風、波など）で足りるか最初に確認する。含まれない項目は、過去分を大量に取りに行かず、直近1〜2年分と今日以降の蓄積に限る。
- **周回展示**：公式の統一データがないため特徴量から外す。場ごとに公開されている一周タイムなどは、今日から蓄積して後で使えるか検討する。
- **IDで結合する**：過去の日別ファイル（Shift-JISの固定長テキスト）と当日のWebページ（HTML）は表記が違う（例：「齊藤」と「斉藤」）。選手名や場名はキーに使わず、登録番号（4桁）・場コード（01〜24）・モーター番号・ボート番号だけで結合する。
- **共通の型に変換する**：日別ファイルの読み取り結果とWebの読み取り結果は、どちらも同じ型定義（Pydanticモデル）に変換してから特徴量づくりに渡す。
- **アクセス数を絞る**：締切前は1レースにつき「直前情報」と「3連単オッズ」の2回だけ取得する。15〜17時頃は全国で締切が重なるため、ジョブが重複起動しないようGitHub Actionsの concurrency を設定する。

## 予想ロジック

各艇の1着確率を出し、そこから全120通りの3連単確率を計算し、期待値が基準を超える目だけを推奨する。

1. **基準モデル（v0）**：コース別1着率と選手の勝率だけで確率を出す。改良の効果を測る物差しにする。
2. **学習モデル（v1以降）**：LightGBMで各艇の1着確率を出す。1行＝1艇で学習し、同じレースの6艇の出力にレース単位でソフトマックスをかける（Group-Softmax、LightGBMのカスタム目的関数）。ランキング学習の出力は確率ではなく、艇番別の多クラス分類は選手の強さを測れないため使わない。補正は温度スケーリング（温度Tを検証データで最適化）で行う。
3. **3連単確率**：Harville方式を基準にし、Henery方式・Stern方式・「2着内率／3着内率モデルを別に学習して組み合わせる方式」を比べる。比較は全120通りの平均だけでなく、(1)1号艇が1着のときと負けたときに分けたLogLoss、(2)確率1〜15%の目に限った補正誤差（ECE）で行い、最も正確なものを採用する。
4. **買い目の選択**：期待値 = 確率 × オッズ。期待値が閾値（初期値1.15）以上の目だけを推奨する。確率1%未満の目とオッズ500倍超の目は除外する。1点もなければ見送り。
5. **買い目数の上限**：1レース最大5点。期待値の高い順に選ぶ。賭け金は最初は均等とし、合成オッズが1倍を下回る組み合わせは推奨しない。

- **欠場艇**：出走取消を検知したら、その艇の確率を0にし、残りの艇で合計1になるよう計算し直してから3連単確率を出す。
- **推奨の条件**：直前情報と直前オッズの両方が取れたレースだけ推奨する。朝のオッズは使わない。

### 特徴量

| 分類 | 特徴量 |
| --- | --- |
| 枠・コース | 枠番、予想進入コース、直前情報の進入 |
| 選手 | 全国勝率、当地勝率、級別、年齢、平均スタートタイミング、フライング持ち |
| 選手の経歴 | 年齢カーブ上の位置（同年代の平均との差）、直近3か月の成績 |
| 機材 | モーター2連率、ボート2連率、部品交換、チルト |
| 直前 | 展示タイムとその順位 |
| 水面・気象 | 風向・風速、波高、潮の満ち引き（潮の影響を受ける場） |
| 場の傾向 | 場名、水面の種類（海水・淡水・汽水）、その場のコース別1着率（直近3〜5年） |

### 学習のルール

- **未来の情報を混ぜない**：勝率・コース別1着率・年齢カーブなどの集計値は、必ず「そのレースの前日までのデータ」だけで計算する。
- **期間比較用の特徴量をそろえる**：3年・5年・10年・全期間のモデルは、2012年以降すべて欠けずにそろう項目だけで学習する。直近しか取れない項目（部品交換など）は、直近データだけで学習する別モデル（2段目）で使う。
- **2段目モデルの学習データ**：1段目の予測値は、ウォークフォワード方式（過去だけで学習→翌月を予測、を1か月ずつ繰り返す）で作ったものだけを使う。最初は2段目を、1段目の確率を土台にした軽いロジスティック回帰にする。
- 学習と検証は時系列で分ける。
- 直前情報なしのモデル（朝の精度測定用）と、ありのモデル（推奨用）を作る。
- モデルは版番号（v0, v1…）で保存し、記録の全行に版を残す。

## 自動答え合わせトラッカー

毎晩自動で答え合わせし、確率の正確さと回収率をモデル別に集計する。

| 表 | 1行の単位 | 主な列 | 入力 |
| --- | --- | --- | --- |
| predictions | レース × モデル | race_id, model_ver, data_window, p1〜p6, 直前情報の有無, skip_reason | 自動 |
| recommendations | 推奨した買い目 | race_id, model_ver, data_window, 組み合わせ, 確率, 15分前オッズ, 確定オッズ, 期待値, 的中, 払戻 | 自動 |
| actual_bets | 実際に買った目 | race_id, 組み合わせ, 金額, 払戻, 収支 | 手入力（data/manual_bets.csv） |

- race_id は「日付_場コード_レース番号」（例：20261112_03_05）。
- 見送りは predictions の行に残し、skip_reason に「期待値不足」「timeout」「欠場」などを入れる。
- actual_bets は手入力とぶつからないよう別ファイルにし、夜の集計時に結合する。
- **返還の処理**：フライング・出遅れ・欠場の艇を含む買い目は、払戻＝賭け金（元返し）として清算する。

### 集計する指標

- **回収率・的中率**：全体、場別、月別、モデル別、推奨ベースと実購入ベース。
- **確率の正確さ**：予想確率をサンプル数が同じになるよう20区間に分け、実際の1着率と比べるグラフ。補正誤差（ECE）、LogLoss、ブライアスコアも出す。
- **見送りの検証**：見送ったレースを買っていた場合の収支。
- **閾値の検証**：期待値の閾値を1.0、1.1、1.15、1.2…と変えた場合の回収率。

集計結果はHTMLのダッシュボードとして出す。

## 遡り期間の比較検証

1. 学習期間だけを変えたモデルを4つ作る：直近3年、5年、10年、取れる全期間。
2. 毎日4つすべてで予想し、data_window 付きで記録する。推奨に使うのは採用中の1つだけ。
3. 3か月ごとに、各レースのLogLossとブライアスコアで比べる。回収率は運に大きく左右されるため、モデル選びには使わない。
4. 現在の採用モデル（初期は5年）との差を、対応のある検定（Diebold-Mariano検定かWilcoxon符号順位検定）で調べ、p<0.05で有意に良い場合だけ切り替える。

- 比較は最低でも1,000レース分たまってから判断する。

## ファイル構成とスケジュール

```
boatrace-predictor/
├─ fetch/
│  ├─ program.py      番組表
│  ├─ results.py      競走成績
│  ├─ beforeinfo.py   直前情報
│  └─ odds.py         3連単オッズ
├─ common/
│  └─ schema.py       共通の型定義（Pydantic）
├─ model/
│  ├─ features.py     特徴量づくり（前日までのデータのみ）
│  ├─ train.py        学習（期間別に4モデル）
│  ├─ predict.py      1着確率→3連単確率
│  └─ select.py       期待値計算・買い目選択
├─ tracker/
│  ├─ settle.py       答え合わせ（返還処理を含む）
│  └─ dashboard.py    集計・HTML出力
├─ notify/
│  └─ discord.py      推奨のDiscord通知
├─ storage/
│  └─ gdrive.py       Googleドライブとの読み書き
├─ data/recent.db     SQLite（直近分と記録）
├─ data/manual_bets.csv  実購入（手入力）
├─ models/            学習済みモデル（版番号付き）
└─ .github/workflows/
   ├─ morning.yml
   ├─ prerace.yml
   ├─ nightly.yml
   └─ retrain.yml
```

| ワークフロー | 時刻（日本時間） | 処理 |
| --- | --- | --- |
| morning | 毎日 8:00 | 番組表取得 → 直前情報なしで予想 |
| prerace | 開催中 10分おき | 締切15〜25分前のレースだけ直前情報・オッズ取得 → 確率更新・買い目選択・通知 |
| nightly | 毎日 22:00 | 成績取得 → 答え合わせ → ダッシュボード更新 |
| retrain | 毎週月曜 3:00 | 4モデルを再学習 |

- 全ワークフローは自宅PCのセルフホストランナー（runs-on: self-hosted）で動かす。自宅PCは開催時間中（8時〜22時頃）と月曜の再学習時に電源とネットを入れておく。PCが止まっていたレースは timeout で見送りになる。
- 定時実行は遅れることがあるため、preraceは第3段階で導入し、間に合わなかったレースは推奨せず見送り（timeout）にする。
- 特徴量は毎回全部作り直さず、毎晩の差分だけ追加する。

## 進め方

- [ ] **第1段階**：過去データの収集、基準モデル（v0）、記録表と答え合わせ（全24場）。15分前オッズと確定オッズの保存も開始。
- [ ] **第2段階**：学習モデル（v1）と遡り期間の4モデル比較
- [ ] **第3段階**：直前情報・オッズの取得、期待値による買い目選択、見送り、Discord通知
- [ ] **第4段階**：場ごとの補正を強化（成績の悪い場は場別モデルを検討）

### Geminiに依頼するときの注意

- 一度に全部ではなく、段階ごとに依頼する。
- 表の列名・ファイル名は、この設計書のとおりにする。
- 学習と検証を時系列で分けること（未来のデータを使わない）を必ず守る。
- 公式サイトへのアクセスは間隔をあけ、取得済みのデータは再取得しない。
- 秘密情報（Webhook URL、Googleのトークン）はコードに書かず、GitHub Secretsから読む。
- 完成したら、v0の予想が過去1か月分で動くかを最初に確認する。
